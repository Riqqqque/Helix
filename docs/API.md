# API Contract

## Status

This document defines the foundation HTTP contract. Endpoint examples beyond the implemented route set are design targets, not proof that a feature exists. Generated API documentation and contract tests should become the authoritative inventory as routes are added.

## Principles

- The API is versioned under `/api/v1` from its first public use.
- Authentication and authorization are enforced on the server for every protected operation.
- Transport handlers do not contain the sole implementation of business rules.
- Mutations validate complete typed input and reject unknown or dangerous ambiguity.
- Long-running operations become jobs rather than holding requests open.
- List responses are bounded and paginated.
- Large uploads and downloads stream with explicit limits and backpressure.
- Errors are safe for users and useful for operators without exposing secrets or internal paths.
- The API reports authoritative state; it does not mirror optimistic frontend assumptions.

## Transport

The initial API uses HTTP with JSON request and response bodies. Server-Sent Events are preferred for one-way live updates. WebSockets are reserved for genuinely bidirectional streams such as an interactive console.

Production deployments must define a trusted TLS boundary, whether direct or through a configured reverse proxy. `helixd` must not trust arbitrary forwarded headers. Request IDs are accepted only in a validated bounded form or generated by the server.

## Current foundation surface and limitations

The implemented loopback-only surface currently exposes:

- `GET /healthz` as a bodyless, database-independent `204` supervisor liveness probe;
- `GET /api/v1/setup/status` as the bounded, non-secret first-run state;
- `POST /api/v1/setup/owner` for one race-safe owner claim using the local one-time token;
- `POST /api/v1/auth/login` for password login;
- `GET /api/v1/auth/me`, `POST /api/v1/auth/csrf`, and `POST /api/v1/auth/logout` for the authenticated session lifecycle;
- `GET /api/v1/health` as the protected detailed health resource;
- `GET /api/v1/system/overview` as a protected, on-demand real host snapshot;
- compiled frontend assets and an SPA fallback for non-API routes.

Unknown `/api` routes return JSON rather than the SPA. Runtime configuration still rejects non-loopback listen addresses because TLS, trusted-proxy handling, MFA, and remote exposure review are not implemented. A separately configured proxy or tunnel must not forward these routes as though that were supported. API failures currently use the bounded `{code, message}` JSON shape; the richer problem format below remains a target.

Except for liveness, setup status, owner claim, and login, current versioned routes require both the `helix_session` cookie and the current `X-Helix-CSRF` proof. The proof is held only in frontend memory. Cookie-only requests cannot read protected data, log out, or rotate a replacement proof. This is required even for `GET` because browser cookies are shared across ports on the same host. Invalid sessions return `401`; a valid session with a missing, malformed, stale, or wrong proof returns `403` with `csrf_rejected`.

## Versioning

The major version is part of the path:

```text
/api/v1/...
```

Within a major version, changes may add optional response fields or new endpoints. Clients must ignore unknown response fields. Removing or changing the meaning of a field, status code, permission, or state transition requires a new major version or a documented deprecation period.

Database schema versions, Sequence schemas, Strand APIs, and frontend asset versions are independent of the HTTP major version.

## Resource conventions

- Stable opaque identifiers are used in URLs. Display names never identify filesystem paths or systemd units.
- Current foundation timestamps are UTC Unix-epoch milliseconds in fields
  whose names end in `_unix_ms` or `UnixMs`. A future representation change
  requires an explicit versioned contract rather than silently changing units.
- Sizes are bytes. Ordinary bounded values use JSON integers; potentially full-range `u64` storage and cumulative-network counters use canonical decimal strings so browser clients do not lose precision above `2^53`.
- Durations use an integer unit named in the field, such as `timeout_ms`.
- Enum values are lowercase machine identifiers; labels are frontend concerns.
- Unknown enum values must fail safely or map to an explicit unknown state.
- Empty, missing, and null retain distinct meanings where the domain requires them.

### Implemented system-overview contract

`GET /api/v1/system/overview` returns one bounded point-in-time host snapshot.
Its `storage.availability` and `network.availability` values are `available`,
`degraded`, or `unavailable`.

- `storage.mounts` contains at most 64 entries. `name`, `file_system`, and
  `mount_point` are nullable; `null` means the host text could not be represented
  safely as non-empty, bounded, control-free UTF-8. `omitted_text_fields` equals
  the represented null-field count, while `omitted_mounts` counts entries lost
  to the response cap.
- Storage `total_bytes`, `available_bytes`, and `used_bytes` are canonical
  decimal strings and must satisfy `used + available = total`.
- `network.interfaces` contains at most 64 entries, each with at most 16
  addresses; at most 256 addresses are returned overall. Omission counts report
  both interface and address truncation.
- Network `total_received_bytes` and `total_transmitted_bytes` are cumulative
  host counters, not transfer rates. Those counters and `mtu_bytes` are
  canonical decimal strings.
- An `unavailable` collector returns no entries or omissions. `available` means
  no entries or representable fields were omitted; otherwise useful results are
  marked `degraded`.

An unlabeled Windows system volume is valid degraded data, for example:

```json
{
  "storage": {
    "availability": "degraded",
    "mounts": [{
      "name": null,
      "file_system": "NTFS",
      "mount_point": "C:\\",
      "total_bytes": "100",
      "available_bytes": "40",
      "used_bytes": "60",
      "read_only": false,
      "removable": false
    }],
    "omitted_mounts": 0,
    "omitted_text_fields": 1
  }
}
```

Collection responses use an envelope so pagination can evolve:

```json
{
  "items": [],
  "next_cursor": null
}
```

Cursors are opaque, bounded, and scoped to the query. Offset pagination may be used only where the data set and consistency requirements make it appropriate.

## Health endpoints

The current unversioned `GET /healthz` route is the package supervisor endpoint. It returns `204 No Content`, performs no database or host sampling, and must not fail solely because an optional module is degraded. Version, dependency state, paths, and host details are deliberately absent.

`GET /api/v1/health` reports detailed readiness and degraded dependencies only to a session authorized for `system.view` with its current CSRF proof. If deployment needs separate liveness and readiness semantics, add explicit probes and package tests instead of changing the meaning of `/healthz` silently.

The unauthenticated liveness response does not reveal host details, version
fingerprints, database paths, or secrets. Detailed health is protected, but
loopback binding remains mandatory until the TLS, proxy-trust, MFA, rate-limit,
and independent-review boundary is implemented and validated.

## Authentication and bootstrap

The first-owner flow is available only while no owner exists and only through the constrained setup state defined by the security model. It must resist a remote race for ownership. Installation should provide a short-lived, one-time bootstrap capability rather than expose an unclaimed administrator form to any reachable client.

Browser sessions use an `HttpOnly`, host-only, `SameSite=Strict`, `Path=/` cookie during the loopback-HTTP phase. `Secure` and the `__Host-` prefix are required when a reviewed HTTPS boundary is implemented. Session identifiers are random, revocable, bounded by idle and absolute expiry, invalidated by authentication-version changes, and stored only as domain-separated hashes.

All protected requests require a session-bound `X-Helix-CSRF` token. Protected mutations also require the exact configured `Origin`; incompatible Fetch Metadata is rejected. The current CSRF rotation endpoint requires the current proof, so the compiled frontend deliberately requires password login after a reload rather than trusting the cookie alone.

Current setup and session payloads use strict camel-case JSON and reject unknown fields. Owner claim accepts `bootstrapToken`, `loginName`, `displayName`, and `password`; login accepts `loginName` and `password`; logout and CSRF rotation require exactly `{}`. Successful owner claim (`201`) and login (`200`) return `user`, `csrfToken`, and `expiresAtUnixMs` while setting the cookie. `GET /api/v1/auth/me` returns `user` and `expiresAtUnixMs`; rotation returns only a replacement `csrfToken`; logout returns bodyless `204` and clears the cookie.

Normal post-convergence state retains at most 64 session rows per user. A login
repairs at most one 256-row excess batch. If a hostile or legacy import is still
oversized, login returns generic `503` code `session_maintenance_in_progress` with
`Retry-After: 1`; the reservation is refunded rather than counted as a password
failure. At the cap, final eviction, credential rehash, new session insertion,
stale pruning, and the success audit record commit atomically.

API tokens are scoped, expiring where appropriate, revocable, and displayed only at creation. Credentials and MFA secrets never appear in ordinary resource representations.

Authentication answers who the actor is. Each domain operation separately authorizes the requested capability and target. UI visibility is not an authorization control.

## Authorization

Permissions use stable capabilities such as `system.view`, `services.control`, `games.configure`, and `backups.restore`. A role is a managed collection of capabilities, not a hard-coded frontend label. Resource-specific grants may narrow access later without changing the basic enforcement point.

Every protected request produces an authorization decision before side effects. Sensitive denials should avoid confirming that a hidden resource exists. Privileged-broker authorization is repeated at the broker boundary rather than inherited blindly from the API.

## Mutations, revisions, and retries

Mutable resources expose a revision or strong validator. Updates require the client to provide the revision it edited, commonly through `If-Match`. A stale mutation returns a conflict response and current safe metadata instead of overwriting another actor's work.

Operations whose retry could duplicate an install, backup, restore, or payment-like side effect accept an idempotency key. The key is scoped to actor, operation, and normalized request. Reusing it with different input is rejected. Results are retained for a documented bounded interval.

Synchronous creation should return `201 Created` with a resource location. Work delegated to the job system returns `202 Accepted` with the job resource:

```json
{
  "job_id": "01...",
  "state": "queued",
  "resource": "/api/v1/jobs/01..."
}
```

An accepted job is not a completed operation.

## Jobs

Planned job resources include:

- `GET /api/v1/jobs/{job_id}` for current authoritative state;
- `POST /api/v1/jobs/{job_id}/cancel` for a policy-checked cancellation request;
- events carrying job progress and state transitions.

Jobs use explicit states such as `queued`, `running`, `cancelling`, `succeeded`, `failed`, `blocked`, and `needs_intervention`. Progress is omitted when it cannot be measured honestly. Cancellation may be delayed or refused at an unsafe commit point; the response explains that state without pretending the work stopped.

## Events

The planned SSE endpoint is `GET /api/v1/events`. Clients authenticate normally, subscribe only to authorized topics, and reconnect with a bounded cursor where supported. Event payloads include an event type, resource identifier, revision, timestamp, and minimal data needed to decide what to refetch.

Metrics samples may be coalesced or dropped for a slow client. Job state and audit records are durable elsewhere; the event channel is not their database. Authorization changes terminate or narrow existing subscriptions promptly.

Interactive consoles use a separate WebSocket endpoint with:

- an authenticated handshake and Origin validation;
- per-instance authorization;
- bounded input and output frames;
- rate limits and backpressure;
- a bounded replay window rather than unbounded in-memory history;
- redaction rules and explicit binary/text handling.

## Target error format

The API should converge on `application/problem+json` with stable machine-readable codes before clients depend broadly on the current skeleton format:

```json
{
  "type": "https://helix.invalid/problems/revision-conflict",
  "title": "The resource changed",
  "status": 409,
  "code": "revision_conflict",
  "detail": "Reload the resource and review the newer revision.",
  "instance": "/api/v1/instances/01...",
  "request_id": "01...",
  "errors": [
    { "field": "revision", "code": "stale" }
  ]
}
```

The `detail` is safe to display but is not a stable programmatic contract. Stack traces, SQL messages, command output, filesystem roots, secrets, tokens, and raw third-party responses stay in redacted operator logs. Validation errors identify fields without echoing sensitive submitted values.

Expected status classes include:

- `400` malformed or semantically invalid input;
- `401` missing or invalid authentication;
- `403` authenticated but not authorized;
- `404` absent or intentionally concealed resource;
- `409` revision, state-machine, lock, or idempotency conflict;
- `413` request or upload exceeds configured limits;
- `422` structurally valid input that cannot satisfy domain rules;
- `429` rate or concurrency limit;
- `503` required dependency unavailable, protective mode active, or bounded
  session maintenance still converging. Retryable responses include an explicit
  `Retry-After` value where the current contract defines one.

## Input and output safety

Every boundary uses typed structures and explicit limits. In particular:

- paths are resource-relative identifiers, not arbitrary host paths;
- uploads enforce byte, file-count, expansion-ratio, and time limits;
- archive extraction rejects traversal, absolute paths, special files, and unsafe links;
- URLs use allowlisted schemes and protect against internal-network request abuse;
- command arguments are structured and never concatenated into a shell command;
- logs and support data are redacted before serialization;
- content disposition and filenames are sanitized independently;
- all user-visible rich text is escaped or sanitized by a narrowly configured renderer.

## Caching

Authenticated API responses default to no shared caching. Sensitive responses use `Cache-Control: no-store`. Immutable hashed frontend assets use long-lived immutable caching; the HTML shell is revalidated. ETags on API resources represent revisions and concurrency, not permission to expose a response through an intermediary cache.

## Rate and concurrency limits

Limits are applied by operation cost and actor, not one arbitrary global number. Login, bootstrap, token creation, archive inspection, searches, and console input need separate policies. Expensive operations also require job-level resource locks and worker limits. A reverse proxy may add protection, but `helixd` retains safe local limits.

## Initial route progression

The foundation should add routes in this order:

1. minimal liveness and readiness;
2. versioned build/API information with no sensitive host detail;
3. constrained owner bootstrap and authenticated session lifecycle;
4. protected host snapshot resources backed by `helix-system`;
5. job and event foundations;
6. privileged administration only after the broker exists and is tested.

Routes must not return fabricated dashboard values while their backend is unfinished.

## Contract testing and documentation

Each route requires tests for success, malformed input, authentication, authorization, stale revisions, limits, and redaction as applicable. An OpenAPI description may be generated or maintained once the route framework is stable, but executable tests remain required. Examples in this document must be updated when the actual contract changes.

The following are not yet validated: public network exposure, TLS/reverse-proxy behavior, independent authentication review, supported-Ubuntu brute-force behavior, API compatibility, reference throughput, browser reconnect behavior, or upload limits. They remain release gates rather than claims.
