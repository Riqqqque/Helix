# Building a Strand

## What is available today

A **Strand** is Helix's extension unit. A Strand may eventually add a dashboard
page or widget, an integration, a notification or backup provider, a health
check, game tooling, an automation action, a bounded API route, or another data
provider.

The current Strand Kit is a **development preview**. It creates and validates a
small package project, but Helix cannot install or execute that project yet.
There is no stable SDK, host ABI, registry, signature format, or Wasm runtime.
That limitation is intentional: package execution waits for the permission,
job, audit, and isolation boundaries listed in [the roadmap](../ROADMAP.md).

The preview is still useful. It gives an extension idea a stable UUID, human
identity, version, compatibility range, explicit permission reasons, and
resource ceilings before implementation grows around an unsafe assumption.

## Create one in under a minute

With a built or installed `helixctl`:

```text
helixctl strand new system-health --name "System Health" --publisher "Your name"
helixctl strand check system-health
```

From a Helix source checkout:

```text
cargo run --locked -p helixctl -- strand new system-health --name "System Health"
cargo run --locked -p helixctl -- strand check system-health
```

The first command creates:

```text
system-health/
├── strand.toml
├── README.md
├── .gitignore
└── src/
    └── README.md
```

The destination must not exist. The generator stages and validates the complete
project before publishing it, and it never has a force or overwrite mode.
Strand tooling does not need a running daemon, initialized database, root
access, or Helix configuration.

Use `--kind ui-only` for a design that will only contribute isolated UI.
`portable` is the default for a future sandboxed component. Trusted native
sidecars are deliberately not generated by this convenience command because
they require a separate high-trust architecture and security review.

## The preview manifest

`strand.toml` is strict TOML. Unknown fields fail closed. The current schema
identifier is `helix.strand/preview-1`, which makes its unstable status
impossible to confuse with a future installable format.

| Field | Purpose |
| --- | --- |
| `id` | Permanent canonical UUID. It survives renames and publisher changes. |
| `slug` | Lowercase machine name used in logs, routes, and package tooling. |
| `name` | Human-facing name. |
| `version` | Semantic Versioning package version. |
| `description` | Short review summary. |
| `license` | Package license or SPDX expression. |
| `publisher` | Human-facing publisher identity for future trust review. |
| `kind` | `portable` or `ui-only` in the preview. |
| `capabilities` | Narrow permissions, each with a human-readable reason. |
| `compatibility` | Bounded Helix range and exact preview host-API generation. |
| `limits` | Requested execution, queue, storage, network, and log ceilings. |

The scaffold starts with **zero capabilities**. When a feature cannot work
without one, replace `capabilities = []` with:

```toml
[[capabilities]]
name = "helix:metrics.read"
reason = "Read the selected node's bounded health summary."
optional = false
```

Capability names must be narrow and canonical. A reason describes the user
benefit, not merely the API call. The eventual installation screen will use
that reason during permission review. A valid preview name does not promise
that the future host API will expose it unchanged.

Resource values are requested ceilings, not reserved memory or guaranteed
throughput. The preview validator accepts only bounded values:

| Limit | Accepted preview range |
| --- | ---: |
| Memory | 8-512 MiB |
| Call time | 10-30,000 ms |
| Concurrent calls | 1-32 |
| Queue depth | 1-1,024 |
| Persistent storage | 0-4,096 MiB |
| Outbound requests | 0-600 per minute |
| Retained log input | 1-1,024 KiB per minute |

Future hosts may enforce smaller limits based on administrator policy and
available capacity.

## Validation behavior

`helixctl strand check PATH` accepts a Strand directory or a direct path to
`strand.toml`. It:

- caps the manifest at 64 KiB before parsing;
- requires UTF-8, strict known fields, canonical UUID and slug forms;
- parses the package version and Helix range as Semantic Versioning;
- requires both a lower and upper compatibility bound;
- rejects duplicate or malformed capabilities and missing reasons;
- validates every requested resource ceiling; and
- prints a short permission and limit summary without running package code.

Malformed data returns a non-zero exit code and field-specific messages, making
the command suitable for a Strand repository's CI:

```yaml
- name: Validate Strand metadata
  run: helixctl strand check .
```

The validator is not a signature verifier, malware scanner, installer, or
sandbox. Package installation will need all of those boundaries independently.

## Recommended author workflow

1. Scaffold the package and commit its stable identity.
2. Write the smallest useful description before requesting capabilities.
3. Add one capability at a time with the concrete user-facing reason.
4. Keep limits near measured needs instead of copying the maximum.
5. Run `helixctl strand check .` in local checks and CI.
6. Discuss any new host API, privileged action, secret access, inbound network
   route, or native sidecar before building around it.
7. Expect preview manifests and experiments to migrate when the stable SDK
   lands.

The checked-in [System Health example](../examples/strands/system-health)
demonstrates a manifest with one read-only capability. It intentionally has no
fake executable component.

## Why execution comes later

Running third-party code safely is much harder than reading a manifest. The
real feature must include capability grant and revocation, a separate optional
host, memory/fuel/time/network/storage limits, namespaced state, isolated UI,
package provenance, rollback, hostile-input tests, and proof that a Strand
cannot reach arbitrary root execution.

Those constraints are the reason Strands can eventually be powerful without
turning the small base daemon into a plugin-shaped security hole. The complete
runtime contract is in [Strand Extension Security and Runtime](STRANDS.md).
